# 独自タイピングシステム 共通仕様の範囲

| 項目 | 内容 |
| --- | --- |
| 文書状態 | コア方針決定済み・API v1確定 |
| 最終更新 | 2026-08-02 |
| 対象 | コンペ主催者、参加開発者、SportEase開発者 |

## 1. 方針

主催者は、システム間の互換性、競技の公平性、正式結果の再現性に影響するコア機能の仕様を決定する。

画面の見た目、使用技術、内部設計、付加機能など、コア機能の契約を変えない部分はコンペ参加開発者の裁量とする。実装者の裁量部分を審査上の工夫として評価できるようにし、共通仕様で過度に制限しない。

判断基準は次のとおりとする。

- 異なる実装でもSportEaseと同じデータを交換できる必要があるか。
- 6人の競技条件や順位に影響するか。
- 同じ入力記録から同じ正式結果を再現するために必要か。
- 無効化、失格、再試合、障害調査に必要か。

いずれかに該当する場合は原則としてコア仕様とする。

## 2. 主催者が決定するコア機能

### C-01 システムの役割分担と正本

- 大会、トーナメント、試合、チーム、選手、正式結果の正本をどちらのシステムに置くか。
- SportEaseとタイピングシステムがそれぞれ保存・管理する範囲。
- 試合開始時に取得した出場情報を固定する方法。

現在の方針では、正式な大会情報と結果の正本はSportEaseとする。

### C-02 SportEaseから情報を取得するAPI

- APIのURLとバージョン。
- 認証方法。
- 大会、競技、トーナメント、試合、チーム、選手、クラス、出場順、レーンの必須フィールド。
- データ型、必須・任意、日時形式、エラー形式。
- 試合開始後に出場情報を意図せず変更しないためのスナップショット規則。

詳細は[SportEase提供API仕様](./typing_system_api.md)で管理する。

### C-03 タイピングシステムが提供する結果API

- APIのURLとバージョン。
- 認証方法。
- 結果一覧・詳細などの必須エンドポイント。
- スコア、元データ、状態、試行、再試合関係の必須フィールド。
- 重複登録を防ぐ結果ID、revision、確定バッチの規則。
- 日時、ページング、エラーの共通形式。

詳細は[確定スコアAPI契約](./typing_system_score_api.md)で管理する。

### C-04 大会・試合・出場者のデータモデル

- タイピング用トーナメントと試合の単位。
- 1チーム3名、1試合6名、全3試合の対応関係。
- `event_id`、`sport_id`、`tournament_id`、`match_id`、`team_id`、`player_id` の意味。
- 出場順とレーンの一意制約。
- 再試合時に同じ試合IDを使うか、新しい試合IDを発行するか。

決定済みの内容として、各タイピング用トーナメントに6人参加の専用試合を3件作り、SportEaseが整数の `match_id` を発行する。再試合では同じ`match_id`を使用し、タイピングシステムが新しい`attempt_id`と結果IDを発行する。

### C-05 試合状態と正式結果の確定

- 待機、準備、競技中、終了、未確定、確定、無効、失格、差し替え済みなどの状態。
- 許可する状態遷移と、各操作を行える主体。
- SportEaseへ渡してよい状態。
- 無効化、失格、訂正、再試合後の正式結果選択。

決定済みの内容として、運営者がタイピング運営画面で確定した1試合6名分だけをSportEaseへ公開する。個別結果の確認UIや内部状態は参加開発者の裁量とする。

API v1では、外部公開状態を`confirmed`、`invalidated`、`disqualified`、`superseded`とし、確定前の`provisional`は公開しない。

### C-06 スコア計算

- 総合スコアの計算式。
- 正タイプ数、誤タイプ数、完了文字数、完了問題数、速度、正確率、競技時間の定義。
- 誤入力の得点への影響。
- 小数の精度と丸め方。
- 同点時の順位決定規則。
- チーム3名分の合計方法。
- 計算式を識別する `formula_version`。

同じ元データと `formula_version` から、どの実装でも同じスコアを再計算できる必要がある。

決定済みの計算式は次のとおりとする。

```text
WPM = 正タイプ数 ÷ 競技時間（秒）× 60
正確率 = 正タイプ数 ÷（正タイプ数 + 誤タイプ数）
総合スコア = floor(WPM × 正確率³)
```

正・誤タイプ数がともに0の場合は、WPM、正確率、総合スコアをすべて0とする。整数スコアが同点の場合は、`floor`前のスコア、正確率、WPM、誤タイプ数の順で比較し、それでも同じ場合は同順位とする。

詳細は[スコア計算仕様](./typing_system_scoring_spec.md)で管理する。

### C-07 タイピング入力判定

- ローマ字入力の共通ルール。
- `shi/si`、`chi/ti`、`tsu/tu`など許可する入力系列。
- 「ん」、促音、拗音、句読点、英数字、記号の扱い。
- 誤入力時に入力位置を進めるか。
- Backspaceによる修正の可否。
- コピー、貼り付け、ドラッグ・アンド・ドロップの禁止。
- 競技終了後に入力を受け付けないこと。

入力判定はスコアと公平性へ直接影響するため、参加者ごとに異なる仕様にはしない。

決定済みの内容として、誤入力時は誤タイプ数を増やすが入力位置を進めない。Backspaceは入力判定上無視し、修正にも誤タイプにも使用しない。基本の複数ローマ字系列、「ん」、促音、小さい仮名の共通規則を使用する。詳細は[入力判定仕様](./typing_system_input_spec.md)で管理する。

### C-08 問題と出題条件

- 問題データの必須項目と複数ローマ字表記の持ち方。
- 同一試合の6名へ同じ問題を同じ順番で表示すること。
- 試合ごとの問題セットと出題順を固定すること。
- 試合開始後の問題変更を禁止すること。
- 問題差し替え時のバージョン管理。

問題管理画面のレイアウトや編集操作の細部は参加開発者の裁量とする。

### C-09 同時開始と時間管理

- サーバー時刻を基準にすること。
- カウントダウン、開始時刻、終了時刻、制限時間の定義。
- 制限時間終了後にサーバー側でも入力を拒否すること。
- 再接続時に残り時間を復元する規則。
- 許容する開始時刻差や時刻同期方法。

WebSocket、Server-Sent Events、ポーリングなどの通信技術は、要件を満たす限り参加開発者が選べる。

途中終了した試合は有効な正式試合として認めない。安全のため停止することはできるが、結果を確定せず無効化して再試合する。有効な試合では設定された競技時間を全6名共通で使用する。

### C-10 競技中の必須機能

- 6台の選手端末を1試合へ割り当てられること。
- 運営者が全員の準備状態を確認し、一括開始できること。
- 運営画面と観戦画面へ6名分の進捗を反映できること。
- 試合の中断、強制終了、無効化、失格、再試合、スコア確定を扱えること。
- 通信切断と再接続を検知できること。

各画面の配置、色、アニメーション、表示項目の選び方は、必須情報と操作を欠かさない範囲で参加開発者の裁量とする。

### C-11 データ整合性と冪等性

- 同じ結果を何度取得しても重複登録しないこと。
- 古いrevisionで新しい正式結果を巻き戻さないこと。
- 6名分の部分確定をSportEaseが正式集計しないこと。
- 出場情報と結果の大会・試合・チーム・選手IDを照合すること。
- SportEaseが一時停止しても確定結果を失わないこと。

### C-12 セキュリティの最低要件

- HTTPSを使用すること。
- APIを認証すること。
- APIキー、トークン、証明書をGitへ保存しないこと。
- 入力値、ID、状態遷移をサーバー側で検証すること。
- 選手・観客が管理操作を実行できないこと。
- APIレスポンスへ不要な個人情報や秘密情報を含めないこと。

認証ライブラリ、秘密情報の注入方法、ネットワーク構成などは、最低要件を満たす限り参加開発者が選べる。

### C-13 障害・再試合判断に必要な記録

- 接続、切断、再接続。
- 試合開始・終了と状態変更。
- 入力結果とスコア計算に必要な元データ。
- 無効化、失格、再試合、確定操作。
- APIアクセス。
- ページ離脱、再読み込みなど指定した異常。

ログの保存形式、検索画面、可視化方法は参加開発者の裁量とする。最低保持期間は主催者が別途決める。

### C-14 適合確認

- SportEaseとのAPI契約テスト。
- 6台同時接続と一括開始。
- 同一問題・同一順序の確認。
- サーバー時刻基準の終了処理。
- 同じ入力記録から同じスコアになること。
- 結果の再取得、無効化、再試合、重複防止。

コンペ提出時に、共通のテストデータまたは適合確認手順で検証できるようにする。

## 3. コンペ参加開発者へ任せる部分

次の項目は、コア仕様を満たす範囲で参加開発者の裁量とする。

- フロントエンド、バックエンド、データベース、リアルタイム通信の技術選定。
- ソースコードの構成、設計パターン、内部API、テーブルの物理設計。
- 選手・運営・観戦画面の具体的なレイアウト、配色、アニメーション、効果音。
- 個別選手の結果をどのように確認・修正してから一括確定するか。
- 選手端末の参加方法。専用URL、参加コード、QRコードなど。
- 進捗、順位、速度、正確率を各画面へどこまで表示するか。
- 問題管理画面の操作方法。
- WebSocket、Server-Sent Events、ポーリングなどの通信方式。
- キャッシュ、キュー、コンテナ分割、監視などの内部構成。
- ログの保存形式と運営者向け検索・表示方法。
- 不自然な高速入力など、追加の異常検知方法。
- 演出、観戦機能、分析表示などの独自要素。

## 4. 主催者の確認が必要になる変更

参加開発者が次を変更したい場合は、独自判断で実装せず主催者へ確認する。

- APIの必須フィールド、型、ID、状態の意味を変える変更。
- スコア計算や入力判定結果が変わる変更。
- 問題順、開始時刻、終了時刻など競技条件が選手ごとに変わる変更。
- 正式結果、無効化、失格、再試合の扱いを変える変更。
- セキュリティの最低要件を弱める変更。

## 5. 仕様管理方法

- この文書を「どこまで主催者が決めるか」の正本とする。
- APIフィールドや状態遷移は個別のAPI契約書で管理する。
- スコア計算、入力判定、問題形式は今後それぞれの仕様書へ分離してよい。
- 決定していない事項は「未決定」または「提案中」と明記する。
- 参加開発者の裁量項目は、API契約書の推奨例を実装必須と解釈しない。
- 仕様変更時は変更日、理由、影響するAPIバージョンを記録する。
