# 独自タイピングシステム 共通仕様の範囲

| 項目 | 内容 |
| --- | --- |
| 文書状態 | コア方針・最小JSON連携仕様決定済み |
| 最終更新 | 2026-08-02 |
| 対象 | コンペ主催者、参加開発者、SportEase開発者 |

## 1. 方針

独自タイピングシステムは、単体で競技を運営できるシステムとする。大会、トーナメント、試合、チーム、選手、問題、競技、結果確認、結果確定、JSON出力までを独自タイピングシステムだけで完結させる。

確定結果は独自タイピングシステムからJSONで出力し、SportEaseの管理画面から取り込む。

主催者は、競技の公平性、正式結果の再現性、JSON互換性、運営に不可欠な機能をコア仕様として決定する。画面の見た目、使用技術、内部設計、付加機能など、コア仕様を変えない部分はコンペ参加開発者の裁量とする。

コンペではこの文書と個別仕様書を正式な要求事項とする。

## 2. 主催者が決定するコア機能

### C-01 単体動作とデータ管理

- 外部サービスへ接続せず、競技運営の全機能を使用できること。
- 大会、トーナメント、3試合、6チーム、16〜18名の代表選手、出場試合、レーンをタイピングシステム内で登録・管理できること。
- 問題セット、競技時間、試合状態、入力記録、計算結果、確定結果をタイピングシステム内へ保存すること。

競技中のデータと未確定・確定結果はタイピングシステムで管理する。JSON取込後のチーム別得点、順位、正式記録はSportEaseで管理する。

### C-02 大会・試合・出場者モデル

- 1つのタイピング用トーナメントを、第1〜第3試合の3試合で構成する。
- 各試合には6チームから1名ずつ、合計6名が出場する。
- `1年生`、`2年生`、`3年生`、`4年生`、`5年生`、`専攻科・教員`の6チームで順位を競う。
- `1-1`〜`1-3`、`IS2`〜`IS5`、`IT2`〜`IT5`、`IE2`〜`IE5`の15クラスから各1名を選び、専攻科・教員チームは1〜3名を選ぶ。
- 各試合へ出場する代表者と出場順は各チームが決定し、システム側で特定の選出元を試合番号へ固定しない。
- 各チームは決定した出場割当を試合開始前に登録する。1〜5年生チームは選出した3名が1試合ずつ出場する。専攻科・教員チームは、1名が3試合すべてに出場しても、複数名が試合ごとに分かれて出場してもよい。
- チームと代表選出元の構成は[参加チーム構成JSON](./typing-team-structure-v1.json)を参照する。このJSONは試合別の代表割当を指定しない。
- 各試合のレーン番号1〜6は重複させない。
- 試合開始後は、その試行の選手、レーン、競技時間、問題セットを変更しない。
- 再試合は同じ試合番号に対する新しい試行として記録する。

### C-03 確定結果JSON

- 3試合すべての結果確定後、6チーム分を1つのJSONとして出力できること。
- JSONにはチーム名、第1〜第3試合の得点、3試合合計、順位だけを含めること。
- 個人名、選手ID、個人成績、入力記録をJSONへ含めないこと。
- SportEaseは管理画面で取込先トーナメントを選択してJSONを取り込み、6チーム分を一括反映できること。
- 同じ`export_id`の再取込で結果を重複登録しないこと。

詳細は[確定結果JSON仕様](./typing_system_results_json_spec.md)で管理する。

### C-04 試合状態と正式結果の確定

- 未開始、準備中、競技中、終了・未確定、確定、無効、失格、差し替え済みを扱えること。
- 運営者がタイピング運営画面で「スコア確定」を実行した1試合6名分だけを`confirmed`とする。
- 自動処理だけで結果を`confirmed`にしないこと。
- 設定時間より前に終了した試合は確定せず、無効化して再試合すること。
- 確定済み数値を直接上書きせず、無効化、失格、再試合の履歴を残すこと。
- システム障害または問題不備の場合は試合全体を無効化し、同じ6名で再試合すること。
- 選手個人の不正は当該選手だけを失格とし、ほか5名の結果を維持すること。
- 個人だけの再試合を認めないこと。
- 再試合の確定後、以前の試行を正式集計から外すこと。

個別選手の結果を確認する画面や、6名分を確定するまでの内部手順は参加開発者の裁量とする。

### C-05 スコア計算

決定済みの計算式は次のとおりとする。

```text
WPM = 正タイプ数 ÷ 競技時間（秒）× 60
正確率 = 正タイプ数 ÷（正タイプ数 + 誤タイプ数）
総合スコア = floor(WPM × 正確率³)
```

- 正・誤タイプ数がともに0の場合、WPM、正確率、総合スコアをすべて0とする。
- 正式な競技時間は180秒とし、全6名共通で使用する。
- 途中終了時の実経過時間を正式スコアへ使用しない。
- チームスコアは3名の整数総合スコアの合計とする。
- 失格選手の当該試合の正式スコアは0とする。
- 同点時は`floor`前のスコア、正確率、WPM、誤タイプ数の順で比較し、それでも同じ場合は同順位とする。

詳細は[スコア計算仕様](./typing_system_scoring_spec.md)で管理する。

### C-06 タイピング入力判定

- ローマ字入力の共通ルールと許可系列を統一すること。
- 正入力の場合だけ正タイプ数と入力位置を進めること。
- 誤入力時は誤タイプ数を増やすが、入力位置を進めないこと。
- Backspaceは無視し、修正にも誤タイプにも使用しないこと。
- 競技終了後の入力を正式スコアへ含めないこと。
- コピー、貼り付け、ドラッグ・アンド・ドロップによる入力を認めないこと。
- 正誤判定、タイプ数、問題進行、終了判定はサーバー側を正本とすること。
- クライアントから合計スコアだけを送信する方式を認めないこと。
- キー長押しのrepeat、Control・Alt・Metaを含む入力、IME入力、判定対象外キーを無視すること。
- 判定対象外キーを誤タイプ数へ含めないこと。
- [主催者の共通入力適合テストJSON](./typing-input-tests-v1.json)で許可された入力系列だけを使用すること。

詳細は[入力判定仕様](./typing_system_input_spec.md)で管理する。

### C-07 問題と出題条件

- 問題データの必須項目と許可文字を統一すること。
- 同一試合の6名へ同じ問題を同じ順番で表示すること。
- 第1〜第3試合で別々の問題セットを使用し、同程度の難易度へ調整すること。
- 問題完了後はEnterなしで自動的に次の問題へ進むこと。
- 句読点は入力対象とし、スペースとShiftを必要とする文字を問題へ含めないこと。
- 試合ごとの問題セットと出題順を固定すること。
- 試合開始後の問題変更を禁止すること。
- 再試合では、無効となった本戦で使用したものとは別の予備問題セットを使用すること。
- 問題セットIDとバージョンを結果へ記録すること。
- [本戦・予備問題プリセットJSON](./typing-problem-presets-v1.json)の本戦3セットと予備7セットを読み込めること。

詳細は[問題・問題セット仕様](./typing_system_problem_spec.md)で管理する。問題管理画面のレイアウトや編集操作の細部は参加開発者の裁量とする。

### C-08 同時開始と時間管理

- サーバー時刻を正式な基準とすること。
- 6名で共通の開始時刻、終了時刻、180秒の競技時間を使用すること。
- 運営者が全員の準備状態を確認して一括開始できること。
- 制限時間終了後はサーバー側でも入力を正式結果へ含めないこと。
- サーバー受信時刻が開始前または終了時刻以後の入力を無効とすること。
- クライアント表示とサーバー記録が異なる場合はサーバー記録を採用すること。
- 選手端末の切断中もサーバー時計を止めないこと。
- 再接続時に同じ選手、レーン、試行、残り時間へ復帰できること。

WebSocket、Server-Sent Events、ポーリングなどの通信技術は、要件を満たす限り参加開発者が選べる。

### C-09 試合状況一括一覧と運営機能

運営者は、選択したトーナメントの全3試合と各試合6名の状況を一括して確認できなければならない。

最低限、次を同じ運営機能内で確認できること。

- 試合番号、試行、試合状態、開始・終了時刻、競技時間。
- 6名のレーン、チーム、代表選出元、選手、出場試合。
- 端末の接続、切断、準備状態。
- 競技中の進捗、正タイプ数、誤タイプ数。
- 終了後のWPM、正確率、総合スコア、確定状態。
- 無効、失格、再試合、差し替えの状態。
- トーナメント全体の確定状況とJSON出力可否。

最低限、次の運営操作を扱えること。

- 6台の選手端末の割り当てと準備確認。
- 1試合6名の一括開始。
- 中断、強制終了、無効化、失格、再試合。
- 1試合6名分のスコア確定。
- 6チームの3試合得点、合計点、順位を含む確定結果JSON出力。

3試合すべての正式結果が揃うまでJSONを出力できないものとする。

一覧のレイアウト、色、カード・表形式、更新方式、追加表示は参加開発者の裁量とする。詳細は[運営・試合状況機能仕様](./typing_system_operations_spec.md)で管理する。

### C-10 選手画面と観戦表示

- 選手端末を指定された試合、選手、レーンへ割り当てられること。
- 選手が自分の準備状態、カウントダウン、問題、入力位置、残り時間を確認できること。
- 運営画面と観戦画面へ6名分の競技状況を自動反映できること。
- 競技終了後は入力を受け付けないこと。

各画面の配置、色、アニメーション、効果音などは参加開発者の裁量とする。

### C-11 データ整合性と重複防止

- 同じ`export_id`を複数回取り込んでも重複登録しないこと。
- JSONは6チーム分を全件成功または全件失敗で処理すること。
- チーム名を取込先トーナメントの正式な6チームと照合すること。
- 各チームの合計点が第1〜第3試合得点の和と一致すること。
- 合計点と順位の大小関係が矛盾しないこと。
- 訂正時は旧結果を履歴へ残し、新しい6チーム分で一括置換すること。

### C-12 セキュリティの最低要件

- 運営機能を認証・認可し、選手や観客が管理操作を実行できないこと。
- 入力値、JSON、ID、状態遷移をサーバー側で検証すること。
- JSONへ個人名、メールアドレス、認証情報、入力キー履歴を含めないこと。
- エラー表示やログへ秘密情報を含めないこと。

認証方式、ライブラリ、ネットワーク構成などは、最低要件を満たす限り参加開発者が選べる。

### C-13 障害・再試合判断に必要な記録

- 接続、切断、再接続。
- 試合開始・終了と状態変更。
- スコア計算に必要な入力集計値。
- 無効化、失格、再試合、確定操作と操作主体。
- JSON出力とSportEaseへの取込結果。
- ページ離脱、再読み込みなど指定した異常。

ログの保存形式、検索画面、可視化方法は参加開発者の裁量とする。最低保持期間は主催者が別途決める。

### C-14 適合確認

- 6台同時接続と一括開始。
- 試合状況一括一覧への状態反映。
- 同一問題・同一順序の確認。
- サーバー時刻基準の終了処理。
- 同じ入力記録から同じスコアになること。
- 主催者の共通入力判定JSONテストにすべて合格すること。
- 6名一括確定、無効化、失格、再試合。
- JSONの構造、型、6チーム、合計点、順位、重複取込。

コンペ提出時に、主催者の共通テストデータと適合確認手順で検証できるようにする。

## 3. コンペ参加開発者へ任せる部分

- フロントエンド、バックエンド、データベース、リアルタイム通信の技術選定。
- ソースコード構成、内部インターフェース、テーブルの物理設計。
- 選手・運営・観戦画面の具体的なレイアウト、配色、アニメーション、効果音。
- 個別選手の結果をどのように確認してから6名分を一括確定するか。
- 選手端末の参加方法。専用URL、参加コード、QRコードなど。
- コア必須項目以外に表示する分析値や演出。
- 問題管理画面の具体的な操作方法。
- WebSocket、Server-Sent Events、ポーリングなどの通信方式。
- キャッシュ、キュー、コンテナ分割、監視などの内部構成。
- ログの保存形式と運営者向け検索・表示方法。
- 不自然な高速入力など、追加の異常検知方法。

## 4. 主催者の確認が必要になる変更

- JSONの必須フィールド、型、得点、順位の意味を変える変更。
- スコア計算や入力判定結果が変わる変更。
- 問題順、開始時刻、終了時刻など競技条件が選手ごとに変わる変更。
- 正式結果、無効化、失格、再試合の扱いを変える変更。
- 試合状況一括一覧から必須情報・操作を省く変更。
- セキュリティの最低要件を弱める変更。

## 5. 仕様管理方法

- この文書を「どこまで主催者が決めるか」の正本とする。
- JSONの構造、得点、順位、取込検証は確定結果JSON仕様で管理する。
- スコア計算、入力判定、問題形式、運営機能は個別仕様書で管理する。
- 決定していない事項は「未決定」または「提案中」と明記する。
- 参加開発者の裁量項目を実装必須要件として扱わない。
- 仕様変更時は変更日、理由、影響する仕様バージョンを記録する。
